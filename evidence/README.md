## 日志行格式

采集器每轮固定输出四类行，时间戳统一为 `MM-DD HH:MM:SS`（UTC+8）：

```
10-21 10:00:08    plan=20 skipped=104                                  ← 本轮计划请求的格子数与跳过数
10-21 10:00:08    HIT 2186/102095 -> 金币 x50000                        ← 逐项发放明细：活动号/任务号 -> 物品 数量
10-21 10:00:08    codes={"RSP": 20} hits=20 lost=False dead=242        ← 本轮响应码分布与命中数
10-21 10:00:08 == poll#1642: OK hits=20 cumulative=15834 ==            ← 累计计数器快照
```

三个字段的语义必须先分清，否则会得出互相矛盾的结论：

`HIT` 行是逐项发放明细，一轮成功 N 次就打 N 行。`codes=` 行的 `hits=` 是该轮的权威计数——2026-10-19 全天 `codes=` 行 `hits=` 求和为 5,055，`HIT` 行数也是 5,055，两者逐轮对得上。

`poll#` 行不是每轮都有，它是采集器的稀疏快照（10-19 全天 333 轮只打了 175 条）。但它的**编号本身即全局轮次序号**，所以可以用它读轮次总数（终值 1,754）；逐轮命中统计仍然只能用 `codes=` 行。`cumulative` 是跨会话累加的单调计数器，只用来定位冻结时刻，不能用来算单日产量 —— 它与 `codes=` 行 `hits=` 求和（21,696 = source `agent16448` 20,411 + source `live` 1,285，即 `_agent16448.log` 与 `_agent_live.log` 两份，可从 `03` 直接复算）相差 5,818，差额原因未知，两者不可互相校验，也不可相加。

## 脱敏处理

已移除：

- 玩家昵称。日志里 `restart: 登录页[welcome:XXX] 已点` 这类登录取证行整行不进切片，原始日志中共出现 5 个不同昵称，一个都没有落进本目录。
- 进程号。`pid=NNN` 与 `running=<pkg>#NNN` 中的数字替换为 `***`。
- 与本研究无关的另一款游戏的日志行，818 条（包名一并省略）。
- 抓包管线行（`tcpdump` / `grab(...)` / `capture(...)`），与奖励发放逻辑无关。
- 会话标识与角色标识：原始日志中不存在这两类字段，无需处理。

保留原样：

- 目标包名 `com.qmzx.ezfy.yxf`、活动号（2186 / 2201 / 2204）、任务号、物品号、物品中文名、数量。
- 全部响应码（`RSP` / `ret571` / `ret154` / `ret205`）与 `lost` / `dead` 标记。
- 全部时间戳，精确到秒。

玩家昵称是唯一被替换的语义内容，替换只影响可读性，不影响任何计数。

### 一处未收敛的归因：`154` 到底是什么

切片 02 中有 8 行 `>> 目标检查：会话 154，等下一轮重启换新会话再看`，以及配套的 `>> 目标检查未成（ERR154）：背包读不到`。这是当时的现场判断：把 `154` 读作会话层拒绝。

后来做过另一组观察：换角色打同一格同样返回 `154`，据此曾推断 `154` 表示「该 `taskId` 不在该角色的活动实例里」。

**两种解释都缺决定性证据，本文不选边。** 支持会话层的实测事实是：全部 486 次 `154` 都伴随 `lost=True`、都出现在轮末、都紧接读背包失败；支持角色-实例解释的是换角色实验，但换角色同时也会让原会话失效，两个变量没能分离。正文 A-06 的表格已把这一格标为「语义未收敛」。

切片中的这 8 行按原始记录保留，不改写当时的现场判断 —— 保留未收敛的现场本身就是可复核性的一部分。

## 复算方法

在仓库根目录执行，三个命令应复现 `03` 聚合表内的合计值。注意 `cumulative` 与 `HIT` 行合计并不相等（见上文），不要拿它们互校：

```bash
# 修复前总命中（按 codes= 行统计，权威口径）
awk -F'\t' 'NR>1 && $1=="agent16448"{s+=$5} END{print s}' evidence/03-hourly-aggregate.tsv

# 修复后总命中
awk -F'\t' 'NR>1 && $1=="live"{s+=$5} END{print s}' evidence/03-hourly-aggregate.tsv

# 分界点前后：10-21 10 点之后、18 点之前是否真的全为零
awk -F'\t' '$2=="10-21" && $3>="11" && $3<="17"{print $3, $5, $6}' evidence/03-hourly-aggregate.tsv
```

单日自洽验证——`01` 文件里 `HIT` 行数与 `codes=` 行 `hits=` 求和应当相等：

```bash
grep -c 'HIT ' evidence/01-before-fix-2026-10-19.log
grep 'codes=' evidence/01-before-fix-2026-10-19.log | grep -oE 'hits=[0-9]+' | cut -d= -f2 | awk '{s+=$1} END{print s}'
```

两条都应输出 `5055`。

## 结论等级

- **实测**：上表全部时刻、计数、响应码分布，均由本目录文件直接支持，可按上面的命令复算。
- **实测**：`ret571` 在 10-21 11:00 之后成为旧活动族的唯一响应码，且重启进程、更换会话、重扫全部 217 格均未改变这一结果。
- **未知**：服务端实际部署修复的精确时刻。可确证的是：10:00:08 那一轮仍全部成功，10:01:39 那一轮已全部被拒，中间轮次编号连续（1642 → 1643），没有停机空档 —— 部署发生在这 **1 分 31 秒**之间，日志无法进一步收窄。
- **未知**：活动 2204 在 18:03–18:14 可领，究竟是因为它属于修复未覆盖的新活动族，还是因为其领取记录表尚未初始化。两种解释都与现有数据相容，日志本身区分不了。
